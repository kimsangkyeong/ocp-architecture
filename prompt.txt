[설계 요구사항 - OCP 4.20+ OVN-Kubernetes gatewayConfig(routingViaHost / ipForwarding) 네트워크 흐름 분석 문서 작성]

역할: OpenShift Container Platform 아키텍처 전문가 + F5(CIS) - OCP Cluster SDN 연동 기술 엔지니어 전문가
전제: 제공 OCP 버전(4.20) 이후 아키텍처 기준으로 정보 제공. 기술 분석/추론은 반드시 근거 site 제공(링크 정상 호출 확인) 하여 cross check 가능하도록 함.

[기본요구사항]
1. 아키텍처/기술 문서는 요구사항에 맞는 폴더를 만들고 하위에 md 파일로 저장.
2. 이미지가 더 적절하면 파일에 이미지 추가(이미지 링크 제공).
3. 2개의 서로 다른 모델로 1개 모델 분석/생성 시 다른 모델로 검증/보완하여 품질 향상.
4. 비용이 많이 소요되면 차선의 비용 절감 방식 제공 후 승인받아 처리.
5. 참고자료는 1개로 머지하지 않고 참고 문서를 만들어 참조하도록 하여 가독성 향상, 원하는 내용에 집중.
6. 변경이력을 문서 맨 앞에 추가하여 변경이력 관리.

[설계요구사항]
1. OCP 4.20 이상 환경에서 OVN-Kubernetes network의 "routingViaHost", "ipForwarding" 설정에 따라
   Pod 기준으로 cluster 내 clusterIP type pod 호출 시 / 외부 서버 node 호출 시 소스 IP, 타겟 IP가 어떻게 되는지
   packet 전달 구조 기준으로 직관적으로 표시.
2. 비교안:
   1안) routingViaHost: true,  ipForwarding: Global
   2안) routingViaHost: true,  ipForwarding: Restricted
   3안) routingViaHost: false, ipForwarding: Global
   4안) routingViaHost: false, ipForwarding: Restricted
3. OCP Cluster 환경: service pool 10.128.0.0/16, pod pool 10.96.0.0/16, machine pool 10.187.0.0/24
   호출 소스: worker node 1(10.187.0.3) - pod A(10.96.1.102)
   호출 타겟1: worker node 1(10.187.0.3) - pod B(10.96.8.8), worker node 3(10.187.0.10) - pod X(10.96.9.9)
   호출 타겟2: 외부 서버 C(192.168.56.7)
   시나리오1: Pod A -> Pod B (port 8080)
   시나리오2: Pod A -> Pod X (port 8080)
   시나리오3: Pod A -> 외부 서버 C (port 443)
4. 시나리오 x 비교안(1~4) 각각 packet 분석 및 통신 가능여부(O/X) 표시. 시나리오별 구성도 + 지정 지점 tcpdump 표시.
   - 시나리오1 tcpdump 지점: 1.pod A, 2.worker node 1, 3.worker node 1, 4.pod B
   - 시나리오2 tcpdump 지점: 1.pod A, 2.worker node 1, 3.worker node 3, 4.pod X
   - 시나리오3 tcpdump 지점: 1.pod A, 2.worker node 1, 3.외부 서버 C
5. 시나리오 구조도 식별 요건: 서버 구분, 동일 Cluster Container에 pod A/B/X 포함 표현(service/pod ip pool/machine pool 정보 추가),
   각 서버/pod IP 표시, tcpdump 소스/타겟 IP:port를 지점에 표시, 통신 불가 영역 식별, 안별 OVN 통신정책 요약/전제사항/가능여부 작성.
6. 맨 마지막에 시나리오/비교안 기준 요약 정리.

[추가 질문 - scenario-3 심화: br-int 의미 / Shared GW multi-NIC egress 인터페이스 선택 / hostNetwork / ipForwarding Global 변경 효과]

1. scenario-3의 2.1 Shared Gateway, 2.2 Local Gateway 구성도에서 br-int 는 cluster 내 OVN이 관리하는 internal bridge network을 의미하는가?

2. Shared Gateway 설정 시 egress가 br-ex(breth0)를 통해 직접 물리 NIC로 나간다는 의미:
   worker node 1에 service 전용 NIC와 NAS 전용 NIC로 구성하고 trident dataplane pod가 NAS 전용 NIC로 통신하려는 경우,
   pod에 spec.hostNetwork: true 가 없으면 통신이 안 되는가?
   기대: 해당 설정 없이도 pod는 node의 port(예: 0.0.0.0:30001) listen만 하고,
   cluster 내 service/pod/다른 서버 IP 호출 시 OVN network이 알아서 필요한 NIC 선택 및 SNAT 처리하기를 기대했는데 가능한가?

3. 우려사항(F5-CIS clusterip mode - OCP 연동):
   우리 환경은 routingViaHost:false, ipForwarding:Restricted 설정. 외부→pod 전달은 잘 되었으나,
   pod→외부서버 호출(scenario-3)이 오류 발생하여 spec.hostNetwork:true 설정으로 정상화.
   그런데 1개 pod에서 외부 서버 호출 후 결과를 다른 pod로 호출하는 경우 hostNetwork 값에 따라 1개만 성공하는 상황 발생.
   해결책으로 NIC에 egress IP 추가 + OVN egress 설정 추가 방식이 제시되었으나 그 설정은 하고 싶지 않음.
   질문: routingViaHost:false, ipForwarding:Global 로 변경하면 성공했을까? 그렇다면 어떤 사유인지 설명 요청.
